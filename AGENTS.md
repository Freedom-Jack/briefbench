# AGENTS.md

Guidance for AI coding agents working in this repository, such as Claude Code, Codex, Gemini CLI and Cursor.

## Start here

Read [docs/design.md](docs/design.md) before changing anything, then the relevant work package in [docs/build-plan.md](docs/build-plan.md). The project is going public: a portable `brief` skill, and a small bench that tests prompting claims against it on the user's own tasks. [docs/design-review.md](docs/design-review.md) explains why the design is what it is.

Use the [agent walkthrough](docs/design.md#agent-walkthrough) to find behavior, symbols and relevant tests, and the [document authority table](docs/design.md#read-this-design-in-layers) to distinguish requirements from history.

[BACKLOG.md](BACKLOG.md) is the standing pending-work queue for sources, maintainer ideas, command/workflow proposals, current and retired claims, and prerequisites. **Every bench continuation must read its "Resume here" section and follow its standard continuation procedure**, even when the user does not name a candidate. Resume the first unblocked authorized task unless the user gives another priority; update its state, blocker and next action before handing off. Do not require the user to reconstruct the article list. The 18 current claim cards are not the full backlog. Keep ideas such as model/effort recommendations and `/goal`/`/loop` command advice visible with their provenance and scope status; tracking them does not relax the rules below or authorize execution.

## Rules

- **Two public entry points.** `brief` is the only frontend skill; `briefbench` is the only backend executable. Use `uv run briefbench bench ...` for the shared bank and its other subcommands for maintenance/studies. Helper scripts, host manifests and experimental variants are internal support, not separate products. Do not add another public entry point without a demonstrated need and maintainer agreement.

- **Keep the two parts separate.** The `brief` skill improves prompts: it clarifies intent and instructions, and once posted settings advice has won a round it may add one note after the brief suggesting the settings to run the task with. It never chooses domain methods, changes the host's settings, does the task, ingests prompting articles, logs, records or evaluates. It works without the bench. The bench runs it headless as a black box and keeps every record itself; the downstream agent owns methods and execution.
- **Only advice people have posted.** The bench tests tricks: advice someone has posted in public about what a prompt says or how it says it, or, since 2026-11-20, about which model, effort level or multi-agent mode to run a task with. Other advice about the agent's setup (tools, project files such as CLAUDE.md, checks outside the model, how several agents are arranged) is out of scope: it gets no claim card and no test. The project's own ideas, 0.2.0's instructions and fixes written after reading a test's losses included, are not tricks, and they never enter the skill unless a post gives the same advice. Test each trick on the kind of work its source is about, in the form the source gives, and name what was actually tested (docs/design.md, "Only advice people have posted"). A trick that enters the skill keeps the condition its source gives, and the skill applies it only when a request meets that condition (docs/design.md, "The skill grows from empty").
- **Keep it cheap.** The bench calls models only through agent CLIs logged in with the user's subscriptions (Claude Code, Codex). Never call a paid API or require an API key, and never let a CLI fall back to one: Claude Code bills `ANTHROPIC_API_KEY` whenever it is set. Keep plan usage light as well: each new trick first runs on the bench, one fixed set of tasks that every trick shares, where the plain prompt's runs are made once and a trick pays only for its own (docs/bench.md). Bench runs are labelled development, not evidence, and run only after the user's yes, with their expected usage stated first. A calibration and a public test run only for a trick the bench flags, after the user's yes, each with its expected usage stated first (docs/design.md, "A method for public results"). Don't build tasks for one trick: a new kind of task joins the bench, for every trick.
- **Stay vendor-neutral.** The core must not depend on any one model vendor or agent harness. Vendor-specific details go in `presets.py`, behind one way of running an agent CLI. The skill uses only the standard Agent Skills fields, plus `disable-model-invocation`, which keeps Claude Code from starting it on its own. Install manifests sit at the repo root (`plugin.json` in the open Agent Plugins format, and `.claude-plugin/marketplace.json`), never inside `skills/brief/`. Only Claude Code and Codex are maintained as install targets for now. A settings note in the skill names settings in terms that work in any host (the host's default effort, one level up, its top level, a smaller or larger model, multi-agent mode on or off), never a model or one host's commands.
- **Build in phases.** Follow the phase order and acceptance checks in docs/build-plan.md. Don't build a later phase's features to work around a blocked gate, and never report a gate as passed without its real evidence.
- **Keep the evaluation hidden and the judge independent.** Neither arm's prompt contains the goal or the check (a Claude Code worker may run exactly the check command, in both arms alike). The judge is always a separate call that can't see which treatment produced which result: it gets the goal, the diffs and the check output, never the prompts, the briefs or the agents' summaries. It comes from neither the worker's vendor nor the rewriter's, and it never decides a trial.
- **Report results honestly.**
  - Show wins, losses and ties, with the tie kinds, and failed and excluded trials.
  - Say whether the results pass the frozen rule's test, and what blocked adoption.
  - Never present a single run or a single pair as an improvement.
- **Keep user data local.** Never write the user's prompts, answers or outputs into the repository. One narrow exception, adopted 2026-11-05: deliberately written public examples and properly licensed public fixtures may be committed after human review, with their provenance and license. The bench handles no API keys: it removes key variables from each agent CLI's environment and scrubs their values from what it prints and logs. The judge sends diffs to its vendor only for repos where the user allowed it.
- **Keep it small.** `SKILL.md` stays at most 150 lines, and the bench near its current 2,900 lines (2,980 on 2026-11-20; docs/design.md, "Decisions at a glance"). Reuse what docs/design.md names before writing new code.
- **Keep dependencies few.** The bench has none at run time. Add one only when it removes real work.

## Working on the code

- When a mapped symbol, behavior or file moves, review the [walkthrough](docs/design.md#agent-walkthrough) in the same change. Keep dated evidence and supersession links; do not add exhaustive symbol lists or import all linked documentation into startup context.
- Run `uv sync`. `uv run pytest` and `uv run --isolated --python 3.14 pytest` must both pass.
- Offline tests use no real agent CLI, no internet and not `~/.briefbench/`. `tests/conftest.py` clears the key variables, points `HOME` and `BRIEFBENCH_HOME` at temporary folders, and fails the run if the real data folder changes. Stand-in agent CLIs are small scripts (`tests/fake_agent.py`). Live tests run real agent CLIs on the user's subscriptions; they are marked `live` and run only with `-m live`. They keep the real `HOME`, where the CLIs keep their logins, and still point `BRIEFBENCH_HOME` at a temporary folder.
- Vendor names, agent CLI names and flags, key variables and default model ids live in `src/briefbench/presets.py`. `tests/test_architecture.py` scans every other `.py` module in `src/briefbench/` for known vendor and model names, comments included, and fails if it finds one.
- The skill's text is what the bench measures: any change to `skills/brief/` starts a new experiment. Bump `metadata.version` with each change, and give `plugin.json` the same version (Claude Code compares it to offer an update; keep it out of the marketplace entry). Add an entry at the top of `CHANGELOG.md` with the folder's bench hash, say so in the commit message, and rebuild the package with `uv run python scripts/package_skill.py`. `tests/test_distribution.py` checks that these agree. Land a skill change on `main` only with its version bump: Codex follows `main` and delivers it as soon as it merges. A release is the tag `brief--v<version>`: pushing it drafts a GitHub release with the ZIP, and the maintainer publishes it.
- The headless request templates in `treatments.py` and the judge prompt are part of the treatments and the evaluation. `init` freezes their hashes (`templates` in the experiment), and `ab` refuses to run an experiment after they change, so a change needs new experiments: say so in the commit message, and bump `experiment.RENDER` when the way a skill becomes a prompt changes.
- The log and experiment formats are a contract with later stages ([docs/data-formats.md](docs/data-formats.md)): add fields, but never rename, remove or reinterpret them.
- Claim cards follow [claims/README.md](claims/README.md); `tests/test_claims.py` checks their format, that no card has a setup kind (`harness` or `practice`), and the rule that only specification, wording and settings claims can fit the skill.
