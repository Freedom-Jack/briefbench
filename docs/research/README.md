# Research

Background research for briefbench: what already exists, what the evidence says about prompting, and how to state a result. These reports inform the design but don't change it. Decisions live in [design.md](../design.md); [design-review.md](../design-review.md) shows where each research recommendation landed, and [design-research.md](../design-research.md) adds later primary-source checks.

Use [the central backlog](../../BACKLOG.md) to track article themes and ideas across these reports, including those with no current claim card. A researched article is not necessarily fully decomposed, eligible for the skill, or experimentally tested. Keep new leads in the backlog while their source, scope and evaluation are resolved.

## Bottom lines

- **Prompt optimizer landscape.** No tool does all three parts of the idea. Of 23 tools reviewed, the closest scores 6 of 8 and has no evidence that it works. GEPA is the only tool whose gains were confirmed outside its authors.
- **Prompting technique benchmarks.** No maintained benchmark ranks prompting techniques. Most parts of briefbench have a precedent, but nothing combines them, and four gaps look open. At personal scale, only large effects will be detectable.
- **Value of prompting techniques.** Phrasing tricks have lost most of their value on frontier models. Specification keeps paying, and the harness moves agent results most. Model-specific prompting belongs to model versions and expires within one or two releases. So the bench should test the brief against the original prompt and re-run when the model changes, rather than rank techniques. The report also tests Felix Rieseberg's essay "How to be more ambitious" and five 2026 posts by well-known practitioners, claim by claim.
- **Benchmark methodology.** For one comparison, the bench already does what careful benchmark reports recommend: paired arms, a hidden automatic check, a rule fixed in advance, exact statistics and every trial counted. Public posts need seven more things: a definition of what is measured, a calibration of the materials on the plain prompt, a number of trials planned from it, a dated public plan with a seed nobody can choose, separate results where a trick should help and where it could hurt, intervals for the cost, and a second test before a trick is marked better. Adopted on 9 Nov 2026 ([design.md](../design.md), "A method for public results"), with four small numerical corrections noted at the top of the report.
- **Settings advice.** Anthropic's and OpenAI's current docs advise settings per kind of task: the default effort for everyday work, more for cases that are easy to miss, the top level only for hard problems the agent works on alone, and multi-agent mode only for work that divides into parts. Independent studies agree that the top level is a poor default, but find the best level hard to predict per task. Neither Claude Code nor Codex lets a skill change the settings the next task runs on. About ten small Claude Code tools already suggest or switch settings, none tested on task results. Seven claims became cards on 20 Nov 2026, when the rule widened to settings advice ([design.md](../design.md), "Only advice people have posted").
- **Agent navigation.** Repository context does not reliably improve coding correctness. Controlled studies support some navigation and efficiency gains, with substantial differences across tasks and tools; stale instructions can add work even when the final fix succeeds. Keep stable instructions concise, reuse the design's architecture map, distinguish current authority from historical evidence, and check local navigation before considering a new index. These are repository-maintenance hypotheses, outside the trick/skill pipeline; no local performance benefit has been established.
- **Trick lifecycle.** Strengthen the existing canonical-claim convention while preserving source conditions, treatments and experiment history. Review adopted instructions when their environment changes, with 30-day source and 90-day instruction reviews checked on next backend use. Use targeted removal comparisons where useful; an old post, a repeated claim or an inconclusive screen does not prove obsolescence. Start with existing records; semantic automation, recurring experiments and a new retirement verdict remain deferred pending need and design review. The maintainer adopted the record/review recommendations on 23 Nov, with [use-triggered timestamp checks](../maintenance.md) instead of scheduled work. Review completion is separate from outcome evidence; no skill efficacy is established.

## How this folder works

- **One folder per topic.** `report.md` is the public report. The table identifies reports exported from a private Claude Doc and reports written in this repository. PNG files accompanying exported reports are images of the doc's interactive charts.
- **Corrections preserve provenance.** Open a pull request against the public report. For an exported report, the maintainer also carries the correction into its private working copy, so the next refresh keeps it. For a report written here, `report.md` is the maintained copy.
- **Refreshing an exported snapshot.** Export each doc tab as Markdown with the Claude Docs connector. Add the snapshot note under the date line, and replace each `[embedded content: …]` chart placeholder with a current image of the chart. This export procedure does not apply to reports written here.
- **The raw research runs are kept privately.** Each run's own outputs (`raw/` folders, git-ignored) are bulky and quote their sources at length; they are not needed to check a report, whose sources are all linked. A local note, `LOCAL.md`, also git-ignored, lists them and the sessions they came from.
- **Adding a topic.** Create a folder with a short kebab-case name, add the report, then add the topic to the table and summary in this file.
