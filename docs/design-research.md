# Research informing the public project design

Research date: 2026-11-04; section 9 added 2026-11-06. This is a repository-maintained design addendum. It supplements the three [research snapshots](research/README.md); it does not edit their live Claude Docs or replace their source records.

> **Updated 2026-11-05.** The sections below were written on 2026-11-04 without knowing that the subscription-CLI bench was already built on 2026-11-03: `init`, `ab`, `score`, `clean` and the judge. It makes every model call through agent CLIs logged in with the user's subscriptions. Where these sections assume a manual-first backend, [design.md](design.md) now governs, and [design-review.md](design-review.md) explains why. This update keeps the research. It corrects what the built bench contradicts: the task population and the baseline (sections 1 and 2), the decision rules (section 5), the public basics (section 6), and smaller points in sections 3, 4 and 7. Section 8 lists what the research led to in the built bench.

The new premise is a public project with one initial maintainer, a useful prompt-enhancement skill and a contribution path for people who want to test prompting advice. The architecture therefore preserves the original source-to-skill purpose while reducing the amount of infrastructure needed to investigate one claim honestly.

## 1. Findings that change the design

| Finding | Design consequence | Evidence strength |
| --- | --- | --- |
| Clearer desired behavior and motivation can improve coding-agent outcomes | Keep consequential clarification as a plausible skill mechanism. Test the skill itself, with its own questions, on its target population: the user's own repo tasks of any type, logged by type | Controlled research in a specific coding benchmark; it does not set the effect size for other task types |
| Separate clarification can help underspecified tasks | A briefing stage is credible, but compare it fairly: in the one-shot handoff, against the same questions and answers unrewritten (`clarified`); against an agent that may ask, in a separate manual study | Research on an underspecified benchmark, not this product's users |
| Prompt rewriting can help while introducing intent risk | Treat fidelity as a requirement and outcomes as the efficacy measure | Older-model real-conversation study with model and author human evaluation |
| Skill format and evaluation conventions already exist | Reuse the format, and do not invent a runtime: daily use runs in the host, and the bench runs the skill's text headless through agent CLIs | Primary format and implementation guidance |
| Paired inference and controlled execution already have tools | Own provenance, fair comparisons and adoption decisions; add adapters only when useful | Current primary project documentation |
| Community evaluation maintenance can become a burden | Support a small reference core; require owners for later task packs | An evaluation project's documented maintenance experience |
| Public contribution needs a shareable artifact policy | Keep private records local and deliberately prepare public fixtures/evidence | Project privacy constraint plus public distribution requirements |

These findings support an experiment and a bounded product design. They do not establish that `brief` improves results, that the bench or any larger backend will pay for itself, or that the project will attract contributors.

## 2. Clarification and rewriting evidence

[RealSWE](https://arxiv.org/abs/2608.27831) varies information composition and style across 381 task families derived from existing software benchmarks. Its abstract reports a 6.4-point average reduction under realistic requests and significant effects from desired behavior and motivation. This supports testing missing intent/context. It does not prove that every added detail helps, that a separate rewriter is necessary, or that the result transfers unchanged to writing, research or analysis tasks.

[Ask or Assume?](https://arxiv.org/abs/2603.26233) reports a 69.4% resolve rate for a scaffold that separates underspecification detection from code execution. Its setting is an underspecified SWE-bench variant. The design inference is that clarification deserves a fair comparison. The bench measures the one-shot handoff, where neither arm can ask anything mid-run. Its default comparison, `original` against `brief`, measures the whole handoff, answers included. Its control for the rewrite alone is `clarified`: the user's prompt with the same questions and answers, unrewritten. A baseline agent that keeps its own opportunity to ask is a different comparison, an interactive session, run by the manual protocol in [experiment-protocol.md](experiment-protocol.md), not by the bench.

[Sarkar et al.](https://arxiv.org/html/2503.16789v2) studies rewriting historical conversations. The revised paper includes a second model evaluator and author human validation, so describing it only as a model judging its own rewrites omits relevant checks. In its intent assessment, 74% received strong preservation ratings, 21% partial ratings and 5% lower ratings. The remaining 26% should not all be described as complete intent loss. Retrospective conversation replay and older models limit what the study says about briefs that current models write from a user's own answers, in a host or headless.

The first task population is the user's own repo tasks of any type, code or documents. Each trial logs its type: code, writing, research, analysis or other. A runnable check decides first, when exactly one arm passes it; the user's blind pick decides otherwise. The 2026-11-04 proposal, document-grounded research and design decisions, fit the motivating use. But every pair would have needed a human judgment, and the [benchmarks report](research/prompting-technique-benchmarks/report.md) says objective checks first ([design-review.md](design-review.md)). The coding-agent studies above don't establish the expected effect size on these tasks. They come closest for code, and say nothing direct about writing, research or analysis. The project must gather its own evidence, and each finding names the task types it covers.

## 3. Official skill guidance and the distinction between development and confirmation

The [Agent Skills specification](https://agentskills.io/specification) defines a directory with `SKILL.md`, required name/description and optional metadata, license and supporting files. This supports the existing packaging choice. Actual host installation, invocation and behavior still require direct checks ([skill-acceptance.md](skill-acceptance.md)).

The official [skill evaluation guidance](https://agentskills.io/skill-creation/evaluating-skills) recommends realistic cases, with/without-skill comparisons, clean contexts, timing capture, human review and objective assertions where possible. It also describes refining assertions after seeing development outputs. briefbench uses that iterative pattern during development, then freezes the comparison with `briefbench init` and confirms it on fresh tasks collected after the last edit. Development iteration is not the same as testing a preregistered claim. The built bench follows the rest of the guidance: a fresh worktree and session for each arm, time and (where the CLI reports them) tokens for each arm, the user's check where there is one, and a blind human pick otherwise.

Anthropic's [agent evaluation guide](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) distinguishes task, trial, grader, transcript and actual environment outcome. The design uses these distinctions to avoid treating a worker's success claim as independent verification. Neither the user, when picking blind, nor the judge sees the agents' own summaries: only the diffs and the check output. The guide's practical advice is useful, but it is not a measured estimate of briefbench's expected gains.

## 4. Build versus reuse

| Component checked | Current capability relevant here | Decision |
| --- | --- | --- |
| evalstats | Statistical comparisons, paired methods and human-label correction of model-judge scores | Optional export for clustered tasks or graded scores; avoid a heavy core dependency for the bench's small exact sign test |
| Inspect | Agent execution, logs and bridges to CLI-based agents | Worktrees and protected paths serve for now. Investigate one adapter when tasks need isolation worktrees can't give; record bridge effects |
| promptfoo | Prompt/test configurations, assertions, repeats and cached evaluation results | Reuse a documented export when actual contributors have one; preserve cache and repeat provenance |
| GEPA | Feedback-driven optimization of supplied targets and evaluation functions | Defer until a stable task population and trusted score exist |
| Agent Skills | Portable frontend instructions and host-oriented testing patterns | Keep the existing skill, with measured host compatibility |

The built bench already reuses Claude Code and Codex as its runners, Arena-Hard-Auto's judge prompt (Apache-2.0) and MT-Bench's both-orders rule ([design.md](design.md), "What to reuse").

The [evalstats repository](https://github.com/ianarawjo/evalstats) and [package metadata](https://raw.githubusercontent.com/ianarawjo/evalstats/main/pyproject.toml) show that inference is already a substantial reusable capability, with scientific Python dependencies. Its [license file](https://raw.githubusercontent.com/ianarawjo/evalstats/main/LICENSE) distinguishes the MIT package from separately licensed website material. Reusing the package does not grant the same rights to copy the website. The product should not claim that significance testing is an otherwise missing invention.

[Inspect's agent bridge](https://inspect.aisi.org.uk/agent-bridge.html) can place existing agents inside an evaluation environment, and [evaluation logs](https://inspect.aisi.org.uk/eval-logs.html) preserve detailed records. A bridge may alter model routing, headers or tool behavior. Treat it as a distinct execution environment unless equivalence to the bench's direct CLI runs is demonstrated. The same caution applies to the bench itself: a headless run is not the same as typing `/brief` in a host, so every finding names its environment. The [project license](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/LICENSE) is MIT; pin an actual compatible release before implementation.

[Promptfoo's test configuration](https://www.promptfoo.dev/docs/configuration/test-cases/) supports per-case repeats and assertions. Its [caching documentation](https://www.promptfoo.dev/docs/configuration/caching/) matters to evidence import: rerunning an evaluation may reuse responses. A repeat index is not itself proof of a fresh generation. An importer must retain cache provenance; a new execution study must use the appropriate fresh-call settings.

[GEPA's repository](https://github.com/gepa-ai/gepa) provides an optimizer and a general optimization interface. That can later generate candidates, but optimization does not supply representative tasks, an independent objective or untouched confirmation data. Initial small human-reviewed variants avoid introducing another system before these prerequisites exist.

No adapter or dependency is selected merely because a feature exists. Before adoption, test one real import/execution against the upstream version, verify licensing for the actual component, and show that the adapter reduces work while preserving the experiment's meaning.

## 5. Why a study has two arms and a decision rule fixed in advance

The [Guardrails Beat Guidance abstract](https://arxiv.org/abs/2604.11088) reports that random rule files matched curated ones on a selected SWE-bench subset using one model/host configuration. This motivates later mechanism controls. It does not make generic padding a required third arm for a whole-workflow usefulness decision, and such text is not guaranteed to be inert.

The original research snapshots disagree on sign-test planning counts. Exact two-sided binomial enumeration at alpha 0.05 and 80% power first reaches the target at 20, 30, 49, 90 and 199 decided pairs for conditional win rates of 80%, 75%, 70%, 65% and 60%. The benchmarks report's 30/90/199 are exact. The value report's 29/85/194 are approximations, not the exact minima. Discrete rejection boundaries make power change irregularly with sample size: at a 75% win rate, 30 decided pairs give 80% power, but 31 and 32 give 77% and 74%. Choose the actual sample after accounting for ties and the frozen rule. The stored research scripts and a separate calculation support the correction, and [design-review.md](design-review.md) recomputed every number on 2026-11-05; the snapshots remain preserved.

The [NIST sign-test reference](https://www.itl.nist.gov/div898/software/dataplot/refman1/auxillar/signtest.htm) describes the binomial sign-test construction. [SciPy's binomial test](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.binomtest.html) supplies an independent implementation and exact intervals for checking numerical fixtures. These references support the test, not the choice of a practical improvement threshold or an affordable human-time cap.

The 2026-11-04 design chose a fixed total task count, one primary comparison and one final analysis for auditability, and treated the built two-look rule as superseded. The reconciled design keeps both rules, each frozen at `init` before the first trial. Two-step is the default, for the user's own adoption decisions, since it stops early when the answer is clear. `fixed:N`, one test after exactly N trials, is for confirmatory or public claims. Section 8 gives both rules' exact numbers. Each experiment still has one primary comparison, A against B. Net preference over all trials, the conditional win rate, ties by kind, fidelity failures and extra cost are all reported, and the pilot times the user's effort. A high win rate among very few decided pairs is not presented as broad usefulness.

The [LLM-as-judge study by Zheng et al.](https://arxiv.org/abs/2306.05685) documents position, verbosity and self-preference biases. This supports blinded comparison and order checks, while leaving the check and the user's blind pick primary. A different vendor and 80% agreement on a small sample are not a calibrated release gate. A judge that decides would need its own calibration protocol ([design.md](design.md), "The judge").

The [reusable-holdout research](https://research.google/blog/the-reusable-holdout-preserving-validity-in-adaptive-data-analysis/) explains why repeated adaptation to evaluation feedback leaks information. briefbench therefore keeps development tasks, such as the pilot's and a variant's first tries, apart from fresh confirmation tasks collected after the last edit. The small frozen set rerun as an upgrade check is separate again, and repeated use makes it development data, not a fresh holdout. A candidate's claim card records its exploratory results and its decision. A variant edited after a failed confirmation goes back to development and needs new tasks; the old tasks don't get a fresh significance allowance.

## 6. Public project and maintenance implications

GitHub's [project-starting guide](https://opensource.guide/starting-a-project/) treats licensing, a useful README and contribution expectations as foundational. The design adopts two user paths and small non-code contributions because the intended audience includes people who can supply evidence or counterexamples without implementing an evaluator.

[Inspect Evals' register rationale](https://github.com/UKGovernmentBEIS/inspect_evals/blob/main/EVAL_REGISTER.md) describes the difficulty of centrally maintaining many evaluations and a move toward externally maintained implementations. Its [register guidance](https://github.com/UKGovernmentBEIS/inspect_evals/blob/main/register/README.md) uses pinned versions, maintainers and run evidence. The lesson is to require ownership and reproducibility for future packs, not to build a registry during the initial phases.

[Promptfoo's contribution guide](https://www.promptfoo.dev/docs/contributing/) asks for focused, validated contributions and contributor accountability. briefbench should likewise accept AI-assisted work while requiring its submitter to explain the change and evidence. A large generated PR is not inherently a useful contribution.

MIT is adopted: LICENSE was added on 2026-11-03, and P0 confirms ownership. Third-party material keeps its own notices, such as the judge prompt's Apache-2.0 license. The narrow public-fixture exception was adopted on 2026-11-05: deliberately written public examples and properly licensed fixtures may be committed after human review, with their provenance and license; private prompts, answers and outputs never are. Private records stay under `~/.briefbench/`, and a private trial never becomes a public fixture by removing a name. A public evidence report should expose its configuration and limitations; it should not redistribute downloaded articles or private conversation logs merely because they informed a study. [Community.md](community.md) specifies the public contribution and publication review process.

## 7. Remaining empirical questions

The next research is primarily local observation rather than another broad web survey:

- How often do the user's real tasks have consequential ambiguity that a brief resolves? Whether a brief also beats an interactive session, where the agent may ask its own questions, is a separate manual comparison, not a bench run.
- Can the user judge real tasks, by a check or a blind pick, at an effort they accept? The pilot times it.
- Does a brief preserve the information obtained during clarification when handed to a fresh worker? The fidelity review records this for each brief.
- Does a current skill variant improve outcomes enough to offset questions, reading and review?
- How noisy are the subscription CLIs, whose model routing and version can't be pinned? Five noise checks flag only gross noise: even no winner in five pairs leaves the true share of pairs with a winner anywhere from 0 to 52% ([benchmarks report](research/prompting-technique-benchmarks/report.md)).
- Do headless briefs behave like those from `/brief` in a host? The bench measures the headless handoff; host behavior needs the acceptance checks.
- Can another person reproduce the protocol without ongoing support, and does the finding transfer to their task population?

P0 checks the skill in real use, P1 measures feasibility, P3 estimates the initial workflow effect, P4 tests a concrete change, and P5 investigates reproduction and transfer. None of these answers is supplied by the absence of a competing all-in-one product.

## 8. Applied on 2026-11-05

The research led to these changes in the built bench on 2026-11-05. [design-review.md](design-review.md) shows where each research recommendation landed, and [design.md](design.md) describes the result. No experiment has run, so none of this shows that the skill improves results.

- **Information kept apart from rewriting.** The value report says to keep two questions apart: does the whole workflow help, and does the rewrite help when both arms have the same information ([value report](research/value-of-prompting/report.md), "What this means for briefbench"). In SkillsBench, skills that models wrote for themselves added nothing on average, so a rewrite may add little beyond the information it carries ([benchmarks report](research/prompting-technique-benchmarks/report.md)). Built: the `clarified` treatment, the user's prompt followed by the skill's questions and the user's answers, word for word; skipped questions are left out. `original` against `brief` tests the whole workflow, and `clarified` against `brief` tests the rewrite alone.
- **The skill's own questions.** Testing a skill means testing it as it is (section 3). Clarifying the goal also lost nearly all its value after the first 10% of an agent's run ([Ask Early, Ask Late, Ask Right](https://arxiv.org/abs/2605.07937), in the [value report](research/value-of-prompting/report.md)). Built: before either arm runs, a headless call lists the questions the skill would ask, as JSON held to a schema, and `ab` puts at most three to the user. A second call writes the brief from the answers and leaves a skipped question open. Before, `ab` asked three fixed questions on the skill's behalf.
- **A hidden goal and check.** Agents that could see a test oracle built to the tests rather than to the request ([Building to the Test](https://arxiv.org/abs/2606.28430), in the [value report](research/value-of-prompting/report.md)). Built: the goal and the check are the evaluation, and neither arm's prompt contains them. The check runs in each worktree after any protected paths, such as the user's tests, are put back from the commit, so an agent that edited them fails. Before, the check command reached the brief arm only. The same report notes that hiding tests entirely also cut legitimate performance in ImpossibleBench. So a finding made with a hidden check doesn't say how either arm would do if it could see the check.
- **Fidelity as a requirement.** About a quarter of rewrites weren't rated as fully preserving intent (Sarkar et al., section 2). Built: after the blind pick, so it can't sway the pick, the user reviews each brief. Did it add a requirement, method, scope or authority? Did it drop or change a detail? Did it change what was asked? Any yes is a fidelity failure, and a failure in any of B's briefs blocks adoption.
- **CLI versions per trial.** Claude Code's built-in system prompt changes between releases ([nilenso](https://blog.nilenso.com/blog/2026/02/10/how-system-prompts-define-agent-behaviiour/), in the [benchmarks report](research/prompting-technique-benchmarks/report.md)), and the value report says to key every record to the model and CLI version. Built: each trial records what `--version` printed for every agent CLI it used. `score` warns when the worker's CLI version or reported model changed during an experiment. Codex doesn't report which model answered, so a Codex result is about the dated CLI default.
- **The judge stays auxiliary.** Pairwise model judges show position, verbosity and self-preference biases ([Zheng et al.](https://arxiv.org/abs/2306.05685)). In that study, GPT-4 gave the same verdict after the two answers swapped places only 65% of the time ([research record](research/prompting-technique-benchmarks/research-record.md)). On code, the best judges predicted developers' preferences 12–23% worse than human annotators ([TRACE](https://arxiv.org/abs/2603.24586), in the [benchmarks report](research/prompting-technique-benchmarks/report.md)). Built: the judge is off by default, and comes from neither the worker's vendor nor the rewriter's. It sees the goal, the diffs and the check output, never the prompts or the briefs. It rules in both orders, and a verdict that flips is a tie. It rules only on trials the user picked, in repos where the user allowed it, and never decides one. `score` reports its agreement with the user's picks, with a Clopper-Pearson interval; the 80%-agreement "trusted" label is gone.
- **The placebo is deferred.** Both reports recommended a placebo arm of similar length, since random rule files helped as much as curated ones in Guardrails Beat Guidance. The 2026-11-04 reasoning in section 5 still holds. That result motivates mechanism studies, but it doesn't make padding a required arm for a whole-workflow decision, and padding isn't guaranteed to be inert. The bench has no built-in placebo. After a workflow result, a mechanism study can add a fixed padding text through `snippet:<file>`, as the [short-briefs claim card](../claims/short-briefs.md) proposes.

**Two decision rules, frozen at `init`.** At personal scale only large effects can be found (section 5), so both rules plan for them. Both use the exact two-sided sign test on decided pairs. Every number below was checked by exact calculation on 2026-11-05.

| Rule | Suits | B is adopted when | Exact properties |
| --- | --- | --- | --- |
| Two-step, the default | The user's own adoption decisions: it stops early when the answer is clear | B wins 16 or more of the first 20 decided pairs, in the order they ran. At 10 or fewer the rule stops. Otherwise it goes on to 40 decided pairs, and B needs 27. If 40 trials leave fewer than 20 decided, the verdict is "no practical difference" | It adopts a useless B 2.2% of the time. It adopts B with a true 75% win rate 89.8% of the time, and with a 65% rate 44.8%. With no effect, it ends at 20 pairs 59.4% of the time |
| `fixed:N` | Confirmatory and public claims, where the sample is fixed in advance | One test once exactly N trials are in, never before. N counts every trial, ties included, from 10 to 1,000. B must be significantly better at the 5% level, with a net preference, (wins − losses) / N, of at least 0.15. A significant loss is reported as harm. Trials after the Nth are reported but not tested | It adopts a useless B at most 2.5% of the time. With N = 50, 25% ties and a true 75% win rate among decided pairs, it finds the effect 85.8% of the time |

Under either rule, B is not adopted if its median extra time or tokens exceed the user's cap, or if any of its briefs failed the fidelity review. Not adopting means no large effect was found, not that there is none. `score` reports the net preference over all trials, with ties counting zero, and a conservative 95% interval. That interval covers at least 95% by construction, and 98–99.9% in every case design-review tried at 20 and 50 trials, so it is wide. `score` also reports the win rate among decided pairs with a Clopper-Pearson interval, and the ties by kind: both good enough, or neither. `score --json` returns every number.

## 9. Distributing and updating the skill, checked 2026-11-06

The question: how do Agent Skills reach people in each host, how do updates follow, and how do popular skill repos number and release versions? Seven research passes read each host's current docs and, where the docs were thin, its source code. A script then found each of the 98 load-bearing claims' quoted fragments on the page it cited: all 98, on 2026-11-06. Most vendor docs carry no date, so they are dated by when they were read; where a page or file shows a date or version, it is given. The local checks at the end used Claude Code 2.1.317 and Codex 0.167.0-alpha.3.2.

**Two open formats.** [Agent Skills](https://agentskills.io/specification) defines the skill folder. It has no version field (its example puts `version` under `metadata`) and says nothing about distribution. It recommends semantic versions, lets a client use `version` to detect updates, and leaves installing and updating to each client. Its [client list](https://agent-plugins.org/compatible-clients) includes VS Code, Cursor, GitHub Copilot, ChatGPT and Codex, but not Claude Code; Claude Code 2.1.317 did read a root `plugin.json` in the local checks.

Most of these repos have no tags: `main` is the release. Where a version exists, it lives in host manifests, either one number copied into each with a check (superpowers' script, trailofbits' CI) or one per plugin. No host reads SKILL.md's `metadata.version` to find updates. The repos that tag use plain `vX.Y.Z` for one repo-wide version; their releases carry notes and rarely files, and a changelog file is rare. The exception is vercel-labs/agent-skills, which makes a release for each commit and attaches an index and one archive per skill. For a repo with separately versioned parts there are three established tag forms: Claude Code's `<name>--v<version>`, which `claude plugin tag` creates and plugin dependency ranges resolve against; release-please's `<component>-v<version>`; and changesets' `<package>@<version>`.

**What briefbench does** ([design.md](design.md), "Files and install"; [community.md](community.md), "Releases and adoption"):
- Only Claude Code and Codex, including the Codex built into the ChatGPT desktop app, are maintained for now (decided 2026-11-06). The other hosts above are left out: no Cursor marketplace file, no `gemini-extension.json`, and no README route for Copilot, Cursor, Antigravity, Gemini CLI, `npx skills`, `gh skill` or the Claude apps. Leaving out `npx skills` also avoids the public skills.sh listing that its first install would create.
- The repo root is an Agent Plugins plugin. `plugin.json` names it and carries the version, and its one skill is `skills/brief/`, unchanged. One one-entry marketplace file, `.claude-plugin/marketplace.json`, lists it, and both hosts read it.
- The version stays out of the marketplace entry, as Claude Code's docs advise; both hosts read it from `plugin.json`. A test checks that `plugin.json` carries SKILL.md's `metadata.version`. Any change to the skill bumps it.
- A release is the tag `brief--v<version>`, which drafts a GitHub release with the ZIP and its hashes. If the bench is ever released, its tags are `bench--v<version>`. One root `CHANGELOG.md` records the skill's versions, each with the bench's hash of the folder, which a test checks; bench headings join it if the bench is ever released.
- The cost: a plugin install copies the whole repository, about 1.1 MB, into each host's cache. Pointing the marketplace at `skills/brief` alone works in Claude Code, but not under Agent Plugins, which finds skills only in `skills/`.
